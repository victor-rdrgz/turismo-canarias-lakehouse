# Contributing

How work is planned, changed, reviewed and released in this repository. The flow is
[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow): branch, changes, pull request,
review, merge, delete the branch.

## Planning

- Planned work (a feature, a data source, a bug, a design question) is tracked as a GitHub issue, created from one
  of the issue forms in `.github/ISSUE_TEMPLATE/`.
- A bug report has the steps to reproduce, the expected result and the actual result.
- Trivial changes (a typo, a broken link, an obvious one-line fix) go straight to a pull request, without an issue.
- Issues are classified with labels: `bug`, `enhancement`, `documentation`, `question` and the project labels
  `area: *` and `priority: high`. Larger work is split into sub-issues; milestones group the issues of a release.
- Design decisions are recorded as ADRs in `docs/adr/`, numbered in order and never rewritten: a new ADR supersedes
  an old one. An ADR is written before the change it describes, from `docs/adr/0000-template.md`, and reviewed in
  a pull request like any other change (as a draft first, to get early feedback). Bug fixes and choices inside an
  accepted ADR need no ADR.

## Branches and commits

- Trunk-based development: `main` is always deployable; work happens on short-lived branches from `main`, one
  branch per set of unrelated changes.
- Branch names: `<type>/<short-description>`, for example `fix/partial-runs`.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/):
  `<type>(<optional scope>): <description>`, with types `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`,
  `chore`. Each commit is one complete, isolated change.

## Pull requests

- Small and focused on one purpose; a large change is split into several pull requests. Pull requests are opened
  against `main` one after another; a pull request is stacked on another only when it needs it.
- The title is a Conventional Commit: pull requests are squash-merged and the title becomes the commit on `main`.
  The head branch is deleted after the merge.
- The description explains the problem, the approach and the result, why the change is needed and where the
  reviewer should look first. The author reviews their own diff before requesting review.
- A pull request is a draft while the work is in progress and is marked ready for review when it should be reviewed.
- The pull request carries a label (`bug`, `enhancement`, `documentation`, ...): the release notes are generated
  from the labels.
- Linking an issue: `Closes #<number>` in the description closes the issue when the pull request merges. GitHub
  honours closing keywords only in pull requests that target the default branch; in a stacked pull request the
  keyword is ignored, so it references the issue as `#<number>` and the keyword is added when the pull request
  targets `main`.
- `main` is protected: a pull request, the `Lint and unit tests` check passing with the branch up to date,
  conversations resolved, linear history, no force pushes or deletions, also for administrators.

## Definition of Done

A change is done when:

1. It has one purpose and is linked to its issue, when there is one.
2. Unit tests cover the new or changed behaviour (a bug fix includes a test that reproduces the bug);
   `uv run ruff check .`, `uv run ruff format --check .` and `uv run pytest` pass.
3. `databricks bundle validate` passes for every target.
4. Changes to jobs, bundle resources or ingestion code are deployed to `dev` and verified with a job run: the job
   succeeds, landing contains the expected run folder and `ops.ingestion_audit` has the expected rows.
5. Design decisions have an ADR; the README, data contracts and runbook are updated when affected.
6. The diff contains no secrets, credentials, personal data or AI assistant files.
7. The pull request has its label.

## Deployment

- `dev`: deployed by each developer with `databricks bundle deploy -t dev` to verify a change before review.
- `staging`: deployed by the CD workflow on every merge to `main`. The workflow runs the ingestion job and the
  integration tests (`tests/integration/`) against it; a failure blocks the next release.
- `prod`: deployed by the CD workflow when a release tag is pushed, after approval in the `prod` GitHub environment.
- Nobody deploys `staging` or `prod` by hand: both are deployed and run by the CI/CD service principal.

## Versioning and releases

- [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`, from `0.y.z` while the platform is in initial
  development. The version lives in `pyproject.toml`.
- Release notes are generated by GitHub from the merged pull requests, grouped by label as configured in
  `.github/release.yml`. There is no hand-written changelog.
- Release steps:
  1. A `chore(release): vX.Y.Z` pull request bumps the version in `pyproject.toml`.
  2. After the merge, and once staging is green for that commit, publish the release from `main`:
     `gh release create vX.Y.Z --target main --title vX.Y.Z --generate-notes`. It creates the tag and the release
     notes.
  3. The tag starts the `prod` deployment; approve it in GitHub Actions. The workflow checks that the tag is on
     `main` and matches the version in `pyproject.toml`.
- A faulty release is fixed forward: revert the change on `main` and publish a new patch release.
